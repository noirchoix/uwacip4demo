# Persistence / Migration Plan

**Do not create the final Alembic revision until the latest `dev` migration head is known.**

Recommended Pipe 4 tables:

```text
current_state_observations
current_state_versions
current_state_version_observations
current_state_current_projection
current_state_access_requests
current_state_watches
current_state_acquisition_requests
current_state_provisional_entities
```

## Key invariants

### observations

- immutable evidence payload after acceptance, except lifecycle/status fields governed by explicit transition logic;
- optional idempotency fields are all-null or all-present;
- unique retry scope is `(actor_user_id, idempotency_operation, idempotency_key)`;
- `idempotency_request_hash` stores the canonical request SHA-256 used to detect conflicting key reuse;
- `observed_at` and `received_at` timezone-aware;
- raw witness text/audio is not duplicated into domain events;
- Knowledge provenance is attached to the observation ID.

### state versions

- append-only truth history;
- one identity key can have many versions;
- predecessor/version sequence is explicit;
- `confidence` nullable;
- `expires_at` nullable;
- no requester identity or decision context inside canonical identity.

### version-observation link

Many-to-many join table. One state version can be supported by multiple observations; one observation may participate in later reconciliation/version decisions.

### current projection

One row per `identity_key`, pointing to the currently selected state version. Publication must append the new version and move this pointer in one transaction after checking the expected current version. A concurrent mismatch must leave both history and projection unchanged by the failed publisher.

### access requests

- `requested_permission` uses the explicit MVP read vocabulary;
- request/approved scopes are JSON representations of the typed `AccessScope`;
- decision actor/time and optional reason remain auditable;
- approval stores the actual approved scope, which may be narrower than requested;
- protected-state access changes never mutate the physical/current state row.

### nearby

First increment stores ordinary latitude/longitude where required and queries through a repository abstraction. Confirm PostGIS in the real environment before using geography types or adding GeoAlchemy2.

## Migration quality

Ernest must verify:

- downgrade works;
- indexes support identity/current/history/nearby/watch queries;
- FKs point only to owner-module public identifiers where approved;
- no migration writes into Knowledge/Identity/Notification tables;
- SQL generated by `alembic upgrade head --sql` is reviewed.
